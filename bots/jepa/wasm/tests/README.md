# Controller parity fixtures

Run the native controller checks without downloading dependencies:

```sh
cd bots/jepa/wasm/controller
cargo test --offline --test semantics
```

`semantics.rs` compares the Rust controller to synthetic fixtures generated by the current table bot's JavaScript
implementation. It does not load a checkpoint, run a game, call a network service, or train a model.

The seven tests cover:

- Twelve feature cases, compared as exact float32 bits and integer IDs: both seats, every action kind, all 32 card
  token slots and their truncation order, live and printed stats, upgrade fallback, aliases, subtype strings, unknown
  cards, duplicate board IDs, missing fields, UTF-8 labels, number formatting, nonfinite option values, and the
  float64-to-float32 boundary after aggregate calculations.
- Fourteen c-clock resource cases: resource and hand thresholds, duplicate aspect requirements, setup versus
  regroup, selected-card limit, the last number in the prompt title, no offered cards, stable ties, and action IDs
  distinct from array positions.
- Eight UTF-8 FNV hash cases and 830 Python-compatible `randrange` draws, including rejection sampling, a full
  MT19937 twist, zero seed, a seed above 32 bits, and the largest exactly represented JavaScript integer seed.
- Twenty controller cases with deterministic model outputs and exact simulator request/reply transcripts: the
  production 0.04 gate, root ordering, Pass outside the root budget, branching follow-ups, Cancel exclusion,
  opponent base targeting, winning and drawing terminals, unchanged-board no-ops, saved follow-up choices despite
  changed card UUIDs, dropped plans, remaining-time fallback, simulation errors, cleanup, and observation loop guard.
- Raw versus evaluator head/horizon routing, mixed horizons, protocol negotiation, and zero/one-action shortcuts.

The controller cases deliberately substitute fixed logits, isolating search and state handling from numerical
inference. They do not establish generated-kernel parity or playing strength. Real wall-clock deadlines, WASI
resource limits, all planner depth/line/step cap combinations, and full-engine games are outside this suite.

The known reference handshake behavior is preserved: imagined mode answers v1 even when the caller offers only v2.
The table's plan mode answers v2 with simulation support. The packaged executable enforces v2 at its boundary and rejects that legacy fallback.

`generate_semantics.js` records the reference source SHA-256 and can regenerate both fixture files. Its default paths
point at this repository's JavaScript, compact synthetic reference JSON, and scripted-simulator helper. For a
different checkout, provide `JEPA_REFERENCE_JS`, `JEPA_REFERENCE_JSON`, and `JEPA_REFERENCE_HELPERS` explicitly.
No model inference occurs during generation; the controller is constructed with deterministic model doubles.

## Loaded-checkpoint runtime parity

`check_runtime.py` separately exercises the diagnostic native and WASI executables with the actual embedded
checkpoints and generated C kernels. It compares all 7 positions × 2 checkpoints × 9 horizons (126 tensor cases per
backend), including every action in the seven-candidate fixture, at absolute tolerance `1e-5`. It checks context
value logits, every action logit, best-action indices, and context reuse across horizons. It also checks seven normal
protocol decisions and replays all six actual-model JavaScript simulator transcripts, with the production gate
`0.04`, through each executable. These include both seats, below-gate decisions, above-gate search, retained
follow-up choices, and the referee's remaining-time fallback.

From the repository root, after building the runtime with its `diagnostics` feature:

```sh
python3 bots/jepa/wasm/tests/check_runtime.py \
  --native bots/jepa/wasm/runtime/target/release/jepa-wasi \
  --wasm bots/jepa/wasm/runtime/target/wasm32-unknown-unknown/release/jepa-wasi.wasm \
  --report bots/jepa/wasm/tests/evidence/runtime-parity.json
```

Python uses only its standard library. `--wasm-runner` defaults to `wasmtime run`; its command prefix is parsed without
a shell. Every reply has a 20-second timeout. `JEPA_CONFIG` is passed to native processes and explicitly forwarded by
Wasmtime, so each bounded scripted case uses its reference search limits. These diagnostic messages are test-only;
the production protocol does not expose them.

The verified run passed both backends with maximum context-value error `1.3485240727417747e-6` and maximum action-logit
error `3.1174978076808912e-6`. Every best-action index, normal reply, scripted simulator exchange and controller
statistic matched. Each tensor sweep performed 14 context encodings and 144 four-candidate prediction calls, with
238 context-cache hits. The evidence JSON records the tested artifact and checkpoint hashes. Its elapsed times are
whole-check verification timings, not decision-latency benchmarks.

`generate_runtime_reference.js` refreshes `fixtures/runtime-reference.json` using the actual JavaScript and checkpoint
files. It retains logits and context values but omits latent arrays to keep the fixture compact. Override
`JEPA_REFERENCE_JS`, `JEPA_REFERENCE_HELPERS`, and `JEPA_REFERENCE_MODELS` for a different checkout. Generation and
verification perform no training, full-engine games, installs or network operations.

`check_production.py` checks the final module without enabling diagnostics: seven ordinary decisions and six exact
JavaScript simulator transcripts, plus rejection of v1-only/string/boolean offers, legacy imagined-mode fallback
and diagnostic requests. Run it with `--wasm build/arena/jepa_tx_gate_wasm/bot.wasm --report /tmp/production-parity.json`.
The report records the actual entry hash. This uses CLI Wasmtime 44; final Arena host checks separately use pinned49.
