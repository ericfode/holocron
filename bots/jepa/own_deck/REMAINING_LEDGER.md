# Opt-in remaining-card ledger

`wasm/controller/src/remaining_ledger.rs` is an isolated, pure data module. It does not change `JepaBot`, its configuration, the WASM graph, checkpoints or competitive policy. The only shared integration change exports the module from `lib.rs`.

The immutable original multiset comes from the actor's own declaration and public card aliases. The mutable ledger records stable instances with separate **original**, **generated** and **external** provenance. Original instances outside the own draw pile subtract once, whether in hand, resources, arena, attachments, capture, discard, removed zones or explicitly transferred outside. Returning one restores its copy. Generated/acquired cards do not consume original copies; if they enter the own pile, they add to its current bag. Metadata-known leader/base/token copies never consume original main-card copies and cannot enter this modeled draw pile.

The API requires an explicitly trusted complete history. `Draw` and unordered `Reveal` batches declare instance provenance; an already tracked instance must match its code, origin and pile membership. Reveal alone does not remove anything. `Create` and `Acquire` establish nonoriginal identities before later draw/move events. `Move` requires the recorded source zone and can represent resource changes, returns, searches, capture and transfers. `Shuffle` changes no membership and retains no order. Event IDs make exact replays idempotent; conflicting replays, duplicate identities, overdraws, unknown origin, history gaps and inconsistent observations fail closed. A failed batch leaves the last consistent instance map intact and marks composition unknown.

`reconcile` accepts only actor-visible typed instances, explicitly complete visible zones and an optional numeric deck size. It rejects private-zone rosters, missing/duplicate/changed identities and unproven new instances. Numeric size is a checksum of an already known bag; it never supplies identities or repairs unknown history. Unknown is sticky until an explicit new-game construction or restoration of the corresponding trusted simulation root. A caller must not use root restoration to erase an observed live-game uncertainty.

`context()` keeps row 0 bitwise fixed and fills the opt-in row 1 from the conserved unordered bag through the existing 207-coordinate encoder. Known current composition can include tracked generated/external cards in the pile; the original row stays fixed. Provenance uncertainty leaves row 1 enabled but unknown, with no guessed content. Metadata-known flags remain defined by the existing serializer: independently missing printed metadata retains its unknown-metadata flag even when instance accounting is conserved. `attach_context` changes only the supplied `Encoded.own_deck` payload. `future(events)` clones the ledger before action/future-target updates; branch mutations and simulated draws cannot mutate the live root. `checkpoint`/`restore` reject different games or original declarations. An unobserved stochastic draw produces an unknown future composition; this module does not invent an exact point target or a draw-distribution training objective.

The ordinary protocol is insufficient to activate this automatically. `engine/view.js` provides stable game-local instance IDs, the actor's hand/resources, public arena/attachments/captures/discard, and numeric deck size. It provides no complete origin/ownership/event history. A newly visible card can be a draw, generated copy or acquisition, and the observation alone cannot distinguish them. Consequently **no runtime remaining knowledge is claimed for ordinary live or simulated observations**. A future adapter must establish the actor-visible event provenance, retain branches independently, and reconcile it before calling these helpers. It must never inspect hidden pile order or opponent private cards. Public catalogue identifiers are used for alias resolution; instance IDs never enter the context tensor.

Validation: `cargo test --offline --manifest-path bots/jepa/wasm/controller/Cargo.toml --lib` passed 24 tests (14 new ledger tests and ten existing library tests). These are pure controller/data tests: no rules-engine application, model inference, games, training or deployment. Coverage includes trusted dealt/mulligan traces, aliases, unordered replay, duplicate/conflicting identities, conservation, resources/attachments/capture/transfers, external/generated pile additions, tokens/base exclusions, reveal/search/shuffle, partial-history/size ambiguity, visible-zone reconciliation, branch/reset, action/future context helpers and serializer-defined metadata uncertainty.
